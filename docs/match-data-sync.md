# Синхронизация данных чемпионата — архитектура и UI

## 1. Проблема

Матч-центр проектировался под ручное ведение матча оператором со стадиона. По факту матчи руками почти не ведутся, и это тянет за собой каскад:

- матчи группового этапа заведены не все и не наполнены;
- финальный раунд Второй лиги (другая структура — 6 групп + плей-офф) не реализован вообще;
- `standingsTable` — singleton с плоским списком `pos/mp/pts`, физически не способен описать 6 групп, рейтинг третьих мест и сетку плей-офф;
- турнирная таблица обновляется руками и устаревает;
- каждый соперник требует ручного создания документа `team` (в схеме `home`/`away` — reference, строкового fallback нет), что делает заведение матча дорогим;
- сайт отстаёт от реального положения дел в чемпионате.

Корень проблемы архитектурный: **единственный путь попадания данных в Sanity — человек**. Решение — сделать основным путём автоматический импорт из внешнего источника, а ручной ввод оставить как override.

## 2. Источник данных

[bel.football](https://bel.football/clubs/polotsk-2019) — Next.js (pages router). Все данные страниц лежат в `__NEXT_DATA__` внутри HTML, то есть доступны без headless-браузера: `fetch` → вырезать `<script id="__NEXT_DATA__">` → `JSON.parse`.

### 2.1. Что откуда берётся

| Страница | Ключ в `props.pageProps` | Что даёт |
|---|---|---|
| `/clubs/polotsk-2019/matches` | `teamProfileMatches[]` | Календарь и результаты клуба |
| `/tournaments/vtoraya-liga/standings` | `tournamentStandingGroups[]`, `tournamentStandingRules[]` | Все 6 групп + «Рейтинг 3 мест» + зоны выхода |
| `/tournaments/vtoraya-liga/matches/<slug>-<id>` | `match.protocol` | Полный протокол матча |
| `/tournaments/vtoraya-liga/matches` | `tournamentMatches[]` | Календарь всего турнира (для сетки плей-офф) |

### 2.2. Формы данных (реальные, проверены 21.09.2026)

**Матч в календаре** (`teamProfileMatches[]`):

```jsonc
{
  "id": "25499",
  "competition": "Вторая лига",
  "tournamentSlug": "vtoraya-liga",
  "seasonLabel": "2026", "seasonSlug": "2026",
  "kickoffIso": "2026-09-25T21:00:00.000Z", "kickoffLabel": "00:00",
  "round": "4 тур", "roundLabel": null, "groupLabel": "Группа B",
  "venue": null, "status": "scheduled",          // scheduled | live | finished
  "homeTeam": "Полоцк-2019", "awayTeam": "Газовик",
  "homeTeamHref": "/clubs/polotsk-2019", "awayTeamHref": "/clubs/gazovik",
  "homeLogo": "https://s3.hostflyby.net/...", "homeBadge": "П2",
  "homeScore": null, "awayScore": null,
  "hasProtocol": false
}
```

**Строка таблицы** (`tournamentStandingGroups[].rows[]`):

```jsonc
{
  "position": 4, "team": "Полоцк-2019", "teamSlug": "polotsk-2019",
  "played": 3, "wins": 1, "draws": 0, "losses": 2,
  "goalsFor": 6, "goalsAgainst": 8, "goalDiff": -2, "points": 3,
  "logoSrc": "https://s3.hostflyby.net/...", "logoLabel": "П2",
  "teamHref": "/clubs/polotsk-2019"
}
```

**Группы и зоны** (`tournamentStandingGroups[]` / `tournamentStandingRules[]`):

```jsonc
// groups
[{"id":"группа-a","label":"Группа A","type":"main","rows":[…6]}, …,
 {"id":"рейтинг-3-мест","label":"Рейтинг 3 мест","type":"extra","rows":[…6]}]

// rules — зоны выхода, готовые цвета
[{"from":1,"to":2,"label":"1/8 финала","scope":"main","color":"#0042aa"},
 {"from":3,"to":3,"label":"Рейтинг 3 мест","scope":"main","color":"#22c55e"},
 {"from":1,"to":4,"label":"1/8 финала","scope":"extra","color":"#00c7fc"}]
```

**Протокол матча** (`match.protocol`) — ключи:
`statusLabel, scoreLabel, dateLabel, roundLabel, venue, referee, attendance, events[], stats[], homeLineup[], awayLineup[], homeSubstitutions[], awaySubstitutions[], homeCards[], awayCards[], homeBench[], awayBench[], homeCoach, awayCoach, homeForm, awayForm`

```jsonc
// events[]
{"minute":"4'","side":"home","type":"goal",      // goal | yellow | red | substitution
 "player":"Михаил Ладутько","playerHref":"/players/mihail-ladutko",
 "assist":"…","photo":"https://…","text":"Гол"}

// homeLineup[] — 11 записей
{"id":"player:12170","number":16,"name":"Макар Маслеников","role":"ВР",
 "href":"/players/makar-maslenikov-86","photo":"https://…"}

// homeSubstitutions[]
{"minute":"37'","inPlayer":{…},"outPlayer":{…}}
```

Покрытие — 1:1 с тем, что уже умеет наша схема `match` (events с типами goal/yellow/red/sub, lineupHome/lineupAway с `positionSlot`, stats). Отдельная схема под импорт не нужна.

### 2.3. Формат финального раунда (то, чего нет на сайте)

Вторая лига 2026, финальный этап (5 сентября — 22 ноября):

- **6 групп по 6 команд** (A–F). «Полоцк-2019» — Группа B: Торпедо-БелАЗ-2, МЛ-Витебск-2, Газовик, Полоцк, БГУ, Друть.
- **Из каждой группы 1–2 место → 1/8 финала** (12 команд).
- **Рейтинг третьих мест**: отдельная сводная таблица шести третьих мест, **4 лучших → 1/8 финала**. Итого 16.
- **Плей-офф**: 1/8 → 1/4 → 1/2 → финал.

Ключевой вывод для модели: **турнир — это не одна таблица, а дерево стадий**, у каждой своя таблица или сетка.

### 2.4. Ограничения источника

- `robots.txt` запрещает `/api`, `/tags`, `/admin` и любые URL с query-параметрами. **Импортёр ходит только на `/clubs/**` и `/tournaments/**` и парсит `__NEXT_DATA__`; JSON-эндпоинты `/api/tags/...` не используем**, хотя технически они отвечают.
- Состав команды (`teamSquadHydrationPath`) грузится именно через `/api/` → под запретом. Состав клуба продолжаем вести в Sanity руками (он и так актуален).
- `buildId` меняется при каждом деплое источника — привязываться к `/_next/data/<buildId>/...` нельзя, только к обычным страницам.
- Crawl-delay не указан; ставим свой лимит (не чаще 1 запроса в 2 сек, ≤ 200 запросов в сутки) и осмысленный `User-Agent` с контактом.
- Перед запуском — написать в bel.football, попросить разрешение на использование и/или официальный фид. Данные (счета, составы) — факты, но отношения лучше оформить. На сайте — атрибуция «Данные: bel.football» со ссылкой на матч.
- Логотипы чужих клубов из чужого S3 не копируем и не хотлинкаем: у `team` уже есть `short` badge — используем его. Логотип грузим только для команд, где это согласовано.

## 3. Модель данных

### 3.1. Новые документы

**`competition`** — турнир
```
name "Вторая лига" · slug "vtoraya-liga" · sourceSlug · kind: league | cup · logo
```

**`season`** — сезон
```
label "2026" · sourceSlug "2026" · isActive · startsAt · endsAt · competition→
```

**`stage`** — стадия (ядро решения)
```
competition→ · season→ · kind: group | extra | playoff
label "Группа B" | "Рейтинг 3 мест" | "1/8 финала"
sourceGroupId "группа-b" · order · isOwnStage (участвует ли Полоцк)
playoffRound: r32 | r16 | qf | sf | final      // только для kind=playoff
```

**`standings`** — таблица одной стадии (заменяет singleton `standingsTable`)
```
stage→ · season→ · sourceUpdatedAt · syncedAt
rows[]: position, team→, played, wins, draws, losses,
        goalsFor, goalsAgainst, goalDiff, points, form[] ("W","L","D",…)
zones[]: from, to, label, color            // из tournamentStandingRules
```

**`importLog`** — журнал запусков
```
job · startedAt · finishedAt · ok · created[] · updated[] · skipped[] · errors[] · rawHash
```

### 3.2. Изменения существующих

**`team`** — `+ sourceSlug` (`polotsk-2019`), `+ aliases[]` (для матчинга «Полоцк-2019» / «Полоцк» / «ФК Полоцк»), `+ needsReview` (создана импортёром, не проверена человеком).

**`player`** — `+ sourceHref` (`/players/ivan-gavin-abff-9687-3bf72b`), `+ sourceId` (`player:23817`), `+ aliases[]`. Это то, что связывает событие из протокола с профилем игрока и оживляет статистику на `/player/[slug]`.

**`match`** — `+ externalId` ("25496"), `+ sourceUrl`, `+ season→`, `+ stage→`, `+ groupLabel`, `+ roundLabel`, `+ hasProtocol`, `+ lastSyncedAt`, `+ syncMode`, `+ sourceProtocol` (сырой протокол на случай конфликта), `+ referee`, `+ attendance`.

`syncMode` — договор между роботом и человеком:

| Режим | Поведение |
|---|---|
| `auto` (по умолчанию) | Импортёр перезаписывает счёт, статус, события, составы |
| `manual` | Матч ведётся руками (live-сессия). Импортёр пишет данные в `sourceProtocol`, основные поля не трогает, в админке показывается diff |
| `locked` | Импортёр не трогает документ вообще (товарищеские, ветеранские, матчи которых нет на bel.football) |

**`standingsTable`** (старый singleton) — мигрируем в `standings` для стадии «Группа B» и удаляем тип.

### 3.3. Детерминированные `_id`

Идемпотентность строится на предсказуемых идентификаторах:

```
match.<sourceSlug>.<externalId>       → match.vtoraya-liga.25496
team.<sourceSlug>                     → team.gazovik
stage.<compSlug>.<seasonSlug>.<gid>   → stage.vtoraya-liga.2026.группа-b
standings.<stageId>                   → standings.stage.vtoraya-liga.2026.группа-b
```

Любой повторный запуск синка — `createIfNotExists` + `patch`, дубли невозможны.

## 4. Пайплайн импорта

### 4.1. Размещение

Новый воркспейс `packages/ingest` (чистые функции: fetch → parse → normalize → diff), вызываемый из двух мест:

- `apps/web/app/api/sync/[job]/route.ts` — Vercel Cron + ручной запуск из админки (защита `Bearer SYNC_SECRET`);
- `apps/studio/scripts/sync.ts` — тот же код для разовых прогонов с ноутбука (бэкфилл, отладка).

Заодно закрывается давняя аномалия: `packages/shared` описан в README, но пуст — либо наполняем его общими типами, либо удаляем упоминание.

### 4.2. Задания и расписание (`vercel.json`)

| Job | Расписание | Что делает |
|---|---|---|
| `fixtures` | `0 4 * * *` (07:00 MSK) | Календарь клуба: новые матчи, переносы дат, смена статуса. Создаёт недостающие `team` и `stage` |
| `standings` | `0 20 * * *` + после `protocol` | Все 6 групп + рейтинг третьих мест + зоны |
| `protocol` | `0 * * * *` в день матча и сутки после | Протоколы матчей, где `hasProtocol && (status==finished) && lastSyncedAt < sourceUpdated` |
| `live` | каждые 2 мин в окно `kickoff−15м … kickoff+150м` | Только если сегодня есть матч Полоцка. Обновляет счёт, минуту, события |
| `playoff` | `0 5 * * 1` | Сетка плей-офф из календаря турнира (после жеребьёвки) |

Cron на Vercel Hobby — 2 задания в сутки. Если тариф не поднимать: один cron `*/5` → внутренний диспетчер, который сам решает, какому джобу пора отработать (по `importLog.finishedAt`). Это же снимает вопрос live-окна.

### 4.3. Алгоритм одного прогона

```
1. fetch страницы → вырезать __NEXT_DATA__ → JSON.parse
2. zod-валидация формы. Провал → НИЧЕГО не пишем, importLog.ok=false, алерт в Sentry
3. нормализация → внутренние DTO
4. резолв сущностей:
   team:   sourceSlug → team | aliases | создать draft с needsReview
   player: sourceHref → player | оставить playerName (схема это уже умеет)
   stage:  groupLabel + season → stage | создать
5. diff с текущим документом Sanity
6. если syncMode=locked → skip
   если syncMode=manual → записать в sourceProtocol, пометить conflict
   иначе → transaction patch
7. importLog + revalidate затронутых путей
```

Устойчивость: любой парсинг обёрнут в zod; при несовпадении схемы прогон падает целиком, а не пишет мусор. Алерт — Sentry (уже подключён) + сообщение в Telegram.

### 4.4. Бэкфилл

Разовый скрипт: пройти по всем матчам сезона, проставить `externalId`/`sourceSlug` существующим документам по совпадению (дата ± 1 день + пара команд), остальное — создать. Отчёт печатается в консоль, запись — только после подтверждения (`--apply`).

## 5. Роль матч-центра

Матч-центр не выбрасывается, а меняет назначение: **из инструмента оператора — в витрину live-данных с ручным override**.

| Сценарий | Кто источник |
|---|---|
| Обычный матч (по факту — почти всегда) | Автоимпорт. До матча — превью, после — протокол в течение часа |
| bel.football ведёт live | `live`-джоб каждые 2 мин, блок показывается с бейджем «автообновление» |
| Важный матч, есть человек на стадионе | `syncMode=manual` → существующая админка, как сейчас. Расхождения с источником видно в diff |
| Товарищеский / ветеранский матч, которого нет на bel.football | `syncMode=locked`, ручной ввод |

Практический вывод: во Второй лиге протокол обычно появляется **после** матча, поэтому основной выигрыш даёт не live, а автоматический календарь, результаты, таблица и пост-матчевый протокол. Live-блок появляется только если источник реально отдаёт `status=live`.

## 6. UI

### 6.1. Главная

- **Hero / ближайший матч** — теперь всегда актуален, без ручного ведения.
- **Блок матч-дня** (эволюция `MatchCenter`) — три состояния:
  - *до*: соперник, тур, дата, форма обеих команд (`homeForm`/`awayForm` из источника), позиции в группе;
  - *во время*: live-счёт и лента (если источник отдаёт);
  - *после*: итог + ключевые события + ссылка на страницу матча.
- **Виджет группы** — компактная таблица Группы B (6 строк, И/О/+−) с подсветкой зоны выхода цветами из `zones[]` и строкой Полоцка.
- **Плашка «Путь в плей-офф»** — «4 место · до зоны 1/8 финала 4 очка · осталось 2 тура». Считается из standings, не требует контента.

### 6.2. Новый раздел `/season` — закрывает финальный раунд

Табы:

1. **Групповой этап**
   - полная таблица Группы B: И В Н П ЗМ ПМ +/− О + форма последних 5;
   - легенда зон (цвета и подписи приходят из источника);
   - ниже — **«Рейтинг третьих мест»** отдельной таблицей: это ровно тот кусок регламента, которого сейчас нет и который решает судьбу Полоцка;
   - сворачиваемый блок «Остальные группы» — A, C, D, E, F.

2. **Плей-офф** — компонент `Bracket`:
   - 1/8 (16 команд) → 1/4 → 1/2 → финал;
   - до жеребьёвки — слоты-заглушки («Победитель группы A», «3-е место, рейтинг»);
   - desktop: 4 колонки с соединительными линиями (SVG, без библиотек);
   - mobile: аккордеон по раундам, горизонтальный скролл только внутри раунда;
   - матч Полоцка подсвечен, клик → `/matches/[id]`.

3. **Все матчи** — календарь с фильтрами (турнир / тур / дом-выезд), группировка по турам, пустые слоты для ещё не сыгранных.

4. **Статистика** — бомбардиры и ассистенты команды, собранные из импортированных протоколов (оживляет уже написанный `player-stats.ts`).

### 6.3. `/matches/[matchId]`

Из roadmap (Спринт 3) переходит в обязательные: протокол, составы обеих команд, замены, карточки, тренеры, форма, судья, посещаемость, атрибуция источника. Всё это уже приходит из импорта — страница становится дешёвой.

### 6.4. Свежесть данных

Под каждой таблицей и в футере матч-дня — строка «Обновлено 21 сентября, 23:40 · данные bel.football» со ссылкой. Если последний успешный синк старше 36 часов — сдержанный бейдж «данные могут быть неактуальны» вместо тихого показа устаревшего.

### 6.5. Админка → «Панель данных»

`/match-admin` перестаёт быть только операторской:

- список матчей со статусом синка: ✓ синхронизирован · ⚠ конфликт с ручными правками · ✋ заблокирован · ● ведётся вручную;
- кнопка «Синхронизировать сейчас» (по матчу и по всему сезону);
- экран **«Несвязанные игроки»** — список `sourceHref` из протоколов, не сопоставленных с профилями, и кнопка привязки в один клик. Это то, что превращает импорт в реальную статистику игроков;
- экран **«Новые команды»** — созданные импортёром `team` с `needsReview`: подтвердить название, добавить badge;
- журнал импортов с диффами;
- существующая live-панель остаётся под тумблером «вести вручную».

## 7. Этапы

| Этап | Объём | Результат |
|---|---|---|
| 0. `externalId`, `sourceSlug`, бэкфилл | 0.5 дня | Существующие данные связаны с источником |
| 1. Импорт календаря и результатов | 1–2 дня | **Сайт перестаёт отставать.** Все матчи группы заведены и со счётом |
| 2. `season`/`competition`/`stage` + `standings` + таблица группы в UI | 1–2 дня | Реальная таблица с зонами выхода вместо плоского singleton |
| 3. Импорт протоколов + маппинг игроков + `/matches/[id]` | 1–2 дня | Наполненные матчи, живая статистика игроков |
| 4. `/season` + плей-офф bracket + рейтинг третьих мест | 2–3 дня | **Финальный раунд реализован** |
| 5. Cron, алерты, индикатор свежести | 0.5 дня | Работает без участия человека |
| 6. Матч-центр в режим витрины, ручной — override | 0.5 дня | Матч-центр перестаёт быть узким местом |
| **Итого** | **6–10 дней** | |

Этап 1 самодостаточен: даже если остановиться на нём, главная боль («сайт сильно отстаёт») закрыта.

## 8. Риски и что с ними делать

| Риск | Митигация |
|---|---|
| Структура `__NEXT_DATA__` у источника поменяется | zod-валидация, при провале — не писать ничего, алерт. Ручной ввод остаётся рабочим всегда |
| `robots.txt` запрещает `/api` | Ходим только на разрешённые страницы, свой rate-limit, честный User-Agent, атрибуция |
| Правовой статус переиспользования | Заранее написать в bel.football; ставить ссылку на источник; не копировать их медиа |
| Ручные правки затираются роботом | `syncMode` + `sourceProtocol` + diff в админке |
| Имена игроков не совпадают | Fallback на `playerName` (схема уже поддерживает) + экран ручной привязки |
| Cron-лимиты Vercel | Один cron `*/5` + внутренний диспетчер джобов |
| Импортёр создаёт мусорные `team` | `needsReview` + экран подтверждения |

## 9. Открытые вопросы

1. Писать ли в bel.football за разрешением / официальным фидом до старта разработки?
2. Нужен ли live-режим вообще, если источник в 90% случаев публикует протокол после матча — или ограничиться пост-матчевым импортом и не тратить cron-бюджет?
